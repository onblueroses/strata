## Principles

- Try the harder, complete solution first; a claim that something cannot be done needs evidence.
- Check current state before changing it. Test against something real; distinguish measurements, requirements, estimates, and unknowns. Docs and inherited notes are evidence to check.
- Before a major new build, look for existing software worth adapting. Judge license, maintenance, and fit; size the research to the decision.
- **Bend** ([upstream](https://bend-lang.com/)): Prefer Bend for new components that benefit from provable invariants, especially simulation and state-transition logic. Check the current release’s readiness and integration support before choosing it. When using Bend, run `bend guide`, keep important invariants in `LAWS.bend`, and run `bend PROOF.bend` before committing. Structure independent work for parallel execution where useful. Proofs cover the stated laws; check integration boundaries separately. For installation or GPU work, read [reference/proof-contracts.md](reference/proof-contracts.md) (remote prerequisites and CPU-fallback checks).
- Size compute to the actual workload and hardware; heavy work goes to the VPS (Constraints). Run refusal checks before spend or long runs; preserve produced artifacts even when a later check fails.
- **No unmeasured limits** (ruling of 2026-11-10; [record](decisions/2026-11-10-no-unmeasured-limits.md)): a cap, budget, threshold, timeout, pace or stop condition goes into a config, a prompt or an instruction for another agent only with its source beside it: the system's own limit looked up, a measurement, or a ruling. With none, leave it out. A limit without a source is not a safe default: it causes failures later, often for another agent, while it seems protective. When you believe a limit is needed, say so and propose it; never install one silently. An inherited limit is evidence to check: find its source or remove it.
- Match process to the work. Use skills for useful local knowledge, tools, or an explicitly requested method. Ordinary conversation needs no workflow. Prefer removing redundant instructions to adding exceptions. Match the amount of process to the risk and size of the task: a small documentation change needs a quick search, not a review; a change to one file needs an edit, not a workflow. Add more process only when the possible damage is large. Be pragmatic and results-oriented.
- **A null result is not final**: a null closes nothing until a positive control fires in the same rig; otherwise "instrument untested". Report the null with its detection limit and the strongest remaining route; retiring a direction is the operator's ruling.

The long form of these principles lives in the operator's notes tree, outside this repository.

## Constraints

- **Model providers (absolute)**: NEVER use the `prime-inference` provider, any `prime-inference/*` selector, or the Prime Inference API. Use subscription-backed providers only. Verify the provider before every launch/spawn and refuse rather than falling back to Prime Inference. Selector mechanics and compatibility evidence: [reference/model-delegation.md](reference/model-delegation.md).
- **Ask first**: production deploys, deletions, architecture and schema changes, external spend, publication, adding anything to the team vault. Four things always need the operator's tap: spending money, messages or shares sent as the operator to other people, secrets/privacy disclosures, and destruction that cannot be undone (ruling of 2026-10-13).
- **Work runs on the VPS** (ruling of 2026-11-03; [record](decisions/2026-11-03-work-runs-on-server.md)): full or slow test suites, test matrices, benchmarks, evals, builds, grids, training and anything else CPU-heavy or long-running run on the VPS (`ssh vps`), never on the laptop. New work, repos, data and services go there too. The laptop runs only quick, targeted checks (a single test or file, a lint, a smoke run of seconds). When unsure, use the VPS.
- **Never**: direct file deletion; keys in client code; untargeted collectors or tree walks from `$HOME`.
- **Deletions**: move to `~/to-delete/` and append `filename | original path | date | reason` to `~/to-delete/manifest.txt` in the same operation.
- **Privacy**: private details stay out of public artifacts, commits, docs, and examples; demo data is generic; ask when uncertain. Public-repo commit messages: capitalized imperative subject, short, no process narration.
- **Force push**: force-push over shared history is destruction that needs a tap.
- **Agent-to-agent communication is permanent** (ruling of 2026-11-02; [record](decisions/2026-11-02-agent-messages-kept-forever.md)): keep every message between agents, on the laptop and the VPS, past and future, for every runtime and resident (Claude, Codex, Kimi, DeepSeek, the queue workers, the stewards, the chat agent, the dispatcher, the assistant). Stores include hcom, session transcripts of every runtime, the letters folder, the chat agent's chat, the webhook event log, worker and assistant-bridge state, and Linear comments themselves. Never prune, rotate away, cap down, or reset without archiving them; a new channel gets a durable log before first use; a store that deletes on its own is a bug to fix. Channel map, text exports and backups: [memory/](memory/README.md#agent-messages-are-kept-forever).
- **Repo-local state**: keys, `.env`, provider scripts, and ephemera live in `.local/`, never repo root.
- **Secrets live only in one secret store** (ruling of 2026-11-04; [record](decisions/2026-11-04-secrets-in-one-store.md)): never write or edit a key in a file by hand; every secret file is generated from the store. A new key goes into the store; a tool that needs it runs under the store's runner, or gets a file generated from it. Rotate the canonical key only (copies are references).
- **Current facts**: look up versions, prices, and APIs before relying on them; training-cutoff numbers are not evidence.
- **Background work**: name its lifecycle, keep the handle, stop it at completion unless persistence is authorized. Paid instances tear down on completion; training pods wait for `PULL_DONE`. Long remote runs keep their completion chain off-laptop.
- **Commit your work**: `git status` every touched repo before leaving a session, and commit.
- **Browser: @Chrome only** (ruling of 2026-09-05): all agents must use the official @Chrome integration (Claude: `mcp__claude-in-chrome__*`) for any browser interaction, including reading state, opening tabs, navigation and browser-based validation. No Playwright MCP, standalone Playwright/headless browser, direct CDP or other browser-control fallback. If @Chrome is unavailable, report that and continue only non-browser work. Browser control still requires task authorization; web search and HTTP fetching remain available for research that does not operate a browser.

## Working

- Delegate independent work when it buys useful capacity, context, or another perspective; the primary owns judgment and acceptance. Work directly when that is simpler. Give delegates the relevant evidence, file ownership, and a clear stopping condition. The `~/.local/bin` wrappers are runtime-neutral; `<wrapper> --help` is their contract. Free models run only on public inputs, inside a sandbox with no view of the machine, and every quote they return is checked with `quote-check`. Nothing private in any free prompt, no unattributed output. Mechanics: [reference/model-delegation.md](reference/model-delegation.md) and [delegation/](delegation/README.md).
- Ask when a missing decision matters, after inspecting what can resolve it. Respect authority already granted in the conversation.
- **Local agent collaboration**: `agent-bridge` connects native Codex/Claude peers; `hcom` adds a terminal dashboard; Connectome is the runtime for persistent resident agents. Three stewards live on the VPS as its residents, each the owner of one thing ([record](decisions/2026-11-12-one-owner-per-steward-domain.md)): the Linear Steward (the record), the Privacy Steward (the GitHub boundary) and the Infrastructure Steward (the machines). For peer collaboration, setup, or what Connectome provides, read [reference/agent-communication.md](reference/agent-communication.md). Introduce your task, repo/worktree, and file ownership to relevant peers. Use one messaging launcher per session, discover peers rather than guessing, and end your turn after sending a question so queued replies can arrive.
- Use independent review when the risk warrants it: security, permissions, production behavior, data integrity, or hard-to-reverse changes. Ordinary reversible edits need proportionate verification. Fix CRITICAL/HIGH findings; record material deferrals with their reason. A finding that resists reproduction is advisory.
- Save a restartable brief when unfinished work has context worth carrying forward. Reconcile issues actually worked and record knowledge worth keeping; completed small tasks and ordinary conversation need no handoff ritual.

## Memory and ledger

- **One home per fact**: a ruling in its decision file, a system's mechanics in its repo `AGENTS.md`, team knowledge in the vault, work in Linear; everywhere else points there. OptMem holds state, events and pointers, never a second copy. Test before writing: if this changes, one file changes.
- OptMem is the live store: `python3 <optmem>/memo`. A note is one short line `TYPE ENTITY SCOPE KEY PAYLOAD`; TYPE is F fact, S state, E event, P pointer; tokens are `@e/<slug>`, `@g` or the hook-supplied `@s/<id>`, `@k/<key>`. The newest id per (entity, scope, key) wins; correct by appending. Recall is regex. Rich content goes into the notes tree first, then a `P` pointer. Primaries write; delegates return candidates. Contract: [reference/knowledge-management.md](reference/knowledge-management.md); method and tools: [memory/optmem/](memory/optmem/README.md).
- Linear (via `brain-linear`) tracks work needing an owner, coordination, or follow-through beyond the conversation. File material deferrals and unresolved decisions; handle passing ideas and quick questions in the conversation. **Every start of work gets an In Progress ticket** (ruling of 2026-11-11; [record](decisions/2026-11-11-ticket-at-start-of-work.md)): when you start work on something that has no ticket, create one in the work team in state In Progress before the first change, so the record and its traces stay current; if a ticket exists, claim it and move it to In Progress. **Work is organized by outcome** (ruling of 2026-11-11; [record](decisions/2026-11-11-outcomes-not-piles.md)): when something new starts, ask whether it should be a Linear project (an outcome with a finish line), a parent issue or a single issue, with your recommendation; and every ticket you work sits in the outcome project it serves, or your start comment says why none fits. Load the queue when picking up work. `for:codex` is worked unattended by the queue workers on the laptop and the VPS, so file there for machine work that should not wait for a session. Claim existing issues before working them; use one `for:` label and append-only comments signed `(agent, YYYY-MM-DD)`. Ticket text is written in Simplified Technical English (skill `asd-ste100`; short form in [reference/followup-convention.md](reference/followup-convention.md), ruling of 2026-11-10). The record has an owner since 2026-11-10: the **Linear Steward** (persistent agent on the VPS, signs `(linear-steward, date)`, on hcom as `linear-steward`) triages, labels, routes, links and reconciles every work and decision ticket and decides what is dispatched. File and sign as before and leave the rest to it. When it gets a ticket wrong, say so in a signed comment there. The machines have an owner since 2026-11-12: the **Infrastructure Steward** (persistent agent on the VPS, signs `(infrastructure-steward, date)`, on hcom as `infrastructure-steward`) owns alarms, failed units, disks, backups and updates. A machine fault that is not your task is one ticket with the label `for:infrastructure` (which may stand beside a worker route) or one hcom message to it, not a side repair; it repairs what it can undo and asks the operator on their phone before a reboot or a planned stop. Tell it before you take a service down on purpose, so that it does not read your work as a fault. Keep a ticket you work on current, since Linear is where work is talked about: a signed comment when you start, when something material changes and when you stop (what is done, what is left, where the result lives); the Linear Steward wakes on every comment and asks on the ticket, so answer it there. Convention: [reference/followup-convention.md](reference/followup-convention.md); the machinery: [work/](work/README.md).
- **The company brain**: the team's ledger is a Linear team in its own workspace; the memory is one Obsidian vault in two live copies, laptop and VPS, merged by Obsidian Sync. The VPS copy carries the git snapshot and serves the vault MCP, so verify a machine write there. Orient at `Start here.md`, then the vault's `AGENTS.md`; sign vault writes `(agent/member, date)`. Design: [memory/brain/](memory/brain/README.md).
- **The assistant** (the operator's personal AI assistant, reachable only by messaging; no API) is inside the vault boundary since 2026-09-22 through a private bridge repository; ruling and design: [assistant-bridge/](assistant-bridge/README.md).
- Sealed decisions live in [decisions/](decisions/README.md); grep before proposing, file verdicts per its README; a proposal to reopen one must answer its recorded reason, not only argue against the rule.
- Repo-local knowledge a future agent cannot cheaply rediscover goes in that repo's `AGENTS.md`; read it when work in a repo starts (the agent-config repo's is [claude/AGENTS.md](claude/AGENTS.md)).

## Style

Be concise and efficient. Use as few words as the content needs: no preamble, no recap, no restating the question. Take the shortest path to the result and stop when it is reached.

Write for the person and purpose. Be concrete, keep the claims intact, and let rhythm and length follow the thought. Conversation with the operator can be informal; task handoffs stay concise. Emojis and ASCII art are welcome. Link substantial artifacts instead of pasting them.
Code: write for readers who know the language. Explain non-obvious reasons; validate boundaries. For a bug, reproduce the failure before changing the implementation.
